# LifeOS 整体逻辑

> 本文只讲结构与运转方式，不讲每个 agent 的具体内容（见 `agents/`）。规则细节见 `docs/core/RULES.md`，换工具接手见 `AGENTS.md` 与 `config/CONFIGURATION.md`。

## 核心思想

**以文件为中心，AI 只是读写文件的“工人”。**

- 文件是唯一事实来源：换模型、换工具、换电脑，读文件即可完整接手。
- 职责分离：**脚本算数，专家判断，管家协调与落盘**。
- 系统分两条线：**生活线**（记录与建议）和**迭代线**（系统自身的改进），互不混放。
- 共享路径和默认值由 `project.json` 登记，共享配置政策由 `config/CONFIGURATION.md` 定义；模型或运行工具的特有差异统一放在 `config/runtimes/`。根目录不再建立 `.claude/`、`CLAUDE.md` 等厂商入口。

```
                       你（文字 / 照片 / 文件）
                              │
                              ▼
                  ┌───────────────────────┐
                  │     管家（主会话）       │  唯一写生活数据的角色
                  │     按「流程」办事        │
                  └──┬─────────┬────────┬──┘
             调用脚本 │   调用专家 │        │ 调用系统 agent
                     ▼         ▼        ▼
              ┌─────────┐ ┌─────────┐ ┌──────────────┐
              │ 脚本     │ │ 领域专家 │ │ 系统迭代师     │
              │ 算数统计 │ │ 只读·判断 │ │ 调研·起草·记录 │
              └────┬────┘ └────┬────┘ └──────┬───────┘
                   └─────┬─────┘             │
                         ▼                   ▼
        ┌────────────────────────────┐ ┌──────────────┐
        │ 生活数据                     │ │ evolve/       │
        │ 档案 日志 领域记录 建议       │ │ 调研 原文 谱系 │
        │ 复盘 洞察 原始数据           │ │ 候选 迭代日志  │
        └────────────────────────────┘ └──────────────┘
```

## 一、数据层（生活线）

| 类别 | 位置 | 作用 | 写入规则 |
|---|---|---|---|
| 档案 | `profile/` | 你是谁、目标、约束、已尝试过的方法 | 可更新，必留变更记录 |
| 每日日志 | `journal/YYYY/` | 一天一篇；数值在 frontmatter，叙述在正文 | 「原始记录」只追加 |
| 领域记录 | `records/<领域>/` | 非每日的数据（购买记录、清单……） | 由负责的专家声明位置 |
| 原始数据 | `inbox/<来源>/` | 外部 API / 导出文件原件 | 永不修改，整理后映射进日志 |
| 餐照与营养记录 | `inbox/meal-photos/`、`records/nutrition/` | 原图、食物与份量推断、营养范围、完整性、目标与复盘依据 | 原图和每餐版本不可改写，更正新增版本；数值估算保留方法和来源 |
| 建议 | `advice/` | 专家每次回答，逐字保存 | 只追加 |
| 复盘 | `reviews/` | 日 / 周 / 月总结 | 按期生成 |
| 长期洞察 | `memory/insights.md` | 被 ≥2 周数据验证的规律 | 只追加 |
| 长期事实与事件 | `memory/entries/YYYY/` | 事实、偏好、单次事件、尝试、临时约束和明确标记的推断，带来源与时间 | 原件不可改写，更正新增记录并关联旧版本；到期不删除 |
| 任务与咨询过程 | `tasks/YYYY/<id>/` | 原始请求、追问、步骤状态、检索结果和专家原文 | 保留过程，按未完成步骤续接 |
| 行动状态 | `actions/YYYY/<id>/` | 每条建议的采纳、执行、延期、拒绝或未知，以及证据 | 状态变化保留历史 |
| 写入快照 | `history/operations/` | 修改前后内容、哈希与操作标识 | 检查冲突、避免重复处理、辅助恢复 |
| 专家知识库 | `experts/<专家>/` | 该领域的个人偏好、资料，以及联网查到并值得复用的知识（含来源） | 随用随补，先查库再联网 |
| 参考数据 | `data/` | 自定义食物；可选的食物成分表（不随系统分发，用户自行生成，见 `data/food/README.md`） | 说明随系统更新；成分表部署时只补缺、不覆盖不删除 |

## 二、能力层

| 角色 | 位置 | 能做什么 | 不能做什么 |
|---|---|---|---|
| 脚本 | `tools/*.mjs` | 计算营养、统计、汇总、列出专家、部署 | 不做判断 |
| 领域专家 | `agents/*.md`（类型=领域） | 读数据、给判断与建议 | 不写文件、不互相对话 |
| 公共规则 | `experts/_common.md` | 所有领域专家共用的工作方式、输出格式、底线 | — |
| 系统 agent | `agents/*.md`（标记 `lifeos:kind=system`） | 改进系统本身（见第五节） | 不回答生活问题、不参与咨询与复盘 |
| 管家 | 主会话 + `docs/core/RULES.md` | 选专家、汇总、裁决冲突、写文件 | 不替专家自评 |

主管家的统一控制规则在 `docs/core/ORCHESTRATOR.md`：复合请求先记录再分析；持久化每次请求；统一事实沉淀；完整保存咨询；独立跟踪行动；保留部分失败并按步骤续接。

请求的生命周期在 `docs/core/CONTROL.md`：执行状态与暂停、等待、取消、替换分开保存。计划通过追加事件修订，保留版本、理由和来源；步骤声明依赖、读写影响、执行尝试和可豁免范围。旧版本结果不会推进新版本，完整完成与带缺口完成分别呈现。新旧请求的替换通过父子关系确认，已有结果与原话不删除。

多年记忆的约定在 `docs/core/MEMORY.md`。原始证据完整保留，逐条记忆记录时间、来源和有效期，工作上下文按问题检索。查询可跨全部年份、按实体过滤、沿显式关系查找，并回查旧日志。当前事实和历史事件分开呈现，失效不等于删除，模型推断不等于事实。该机制适用于所有生活领域；症状只是其中一个事件例子。

冲突优先级：**健康安全 > 睡眠恢复 > 你的目标优先级 > 其他**。

所有领域遵守共享配置中的 Voluntary disclosure and privacy：个人信息可选，默认及领域偏好保存在同一份用户配置中。主管家、专家、初始化、检索和审查先检查限制；拒绝的字段不能通过其他角色或旧记录补推。隐私工具只读计算生效偏好，启动脚本仅报告日志是否存在。缺少信息会限制建议的具体程度，不会自动要求填写完整档案，也不会删除既有原件。

## 三、流程层（生活线）

| 流程 | 做什么 |
|---|---|
| `/log` 记录 | 原话存档 → 分拣到各段 / 领域记录 → 脚本算营养 → 汇总 |
| `/import` 导入 | 原件存入 inbox → 按来源说明映射进日志 → 冲突不覆盖、只标注 |
| `/ask` 咨询 | 选一位专家 → 读数据作答 → 逐字存档 → 对话后沉淀 |
| `/panel` 会诊 | 主导 + 辅助专家 → 审查原始建议 → 管家汇总 → 审查最终方案并核实整改 → 存档 → 沉淀 |
| `/review` 复盘 | 脚本出数据 → 检查上期建议执行情况 → 相关专家评估 → 写复盘 → 规律入洞察 |
| `/setup` 档案 | 分轮提问，边问边写 |

**对话后沉淀**：每次咨询 / 会诊后，把新出现的目标、约束、已尝试过的方法、新事实写回档案或专家知识库。

**审查闭环**：统一规则在 `docs/core/REVIEW.md`。会诊必须审查，单专家咨询与周/月复盘在重大不确定性、冲突、重要投入、安全问题或用户明确要求时审查；简单记录和描述性日复盘沿用轻量流程。审查员核对原始资料和长期历史，把问题分为阻断、重大、一般；主管家记录如何处理，重大问题由审查员核实。最终方案与审查通过的具体文件版本绑定，之后改动必须重审。默认最多三轮最终审查，设置在 `project.json`，超过后保留结果与未解决问题。

审查过程和每轮原文保存在任务文件中。`review_gate` 是不可随意豁免的验证步骤，脚本检查版本、文件哈希和问题处理记录，最终存档再次检查实际回答；这些检查不代替模型对证据的判断。单纯评审用户已有方案可以给出“不通过”并完成评审请求，不代表方案获准执行。

**闭环**：

```
记录 → 咨询/会诊 → 建议（存档）→ 执行 → 继续记录
  ↑                                        │
  └── 沉淀规律 ← 复盘（检查执行与效果）←───┘
```

用得越久，档案越完整、洞察越多，建议越贴合你。

**提示词与交互语言分离**：维护的角色定义、操作流程、公共规则和模型入口使用英文；用户交互语言在首次部署后的初始化对话中确认，默认中文。选择保存在 `profile/preferences.json`，由所有角色共同读取，换模型继续生效，升级不覆盖。个人数据原话与历史文件保留原语言，日志的既有标题和表头作为存储格式保留。

## 四、扩展（加东西不用改原有结构）

日报规则在 `docs/domains/REPORTING.md`：主管家在晨间睡眠记录及分析完成后，生成前一天的数据与行动报告，睡眠仍按醒来日保存。JSON/Markdown/HTML/PDF 是可追溯的不可覆盖衍生版本；数据完整性、行动实际状态和待协调问题分开呈现。可选 PDF 库安装在同步库外，中文字体嵌入输出；没有固定早八任务或后台文件监听，也没有新增报告专家。

旅行共享规则在 `docs/domains/TRAVEL.md`：`travel-planner` 按需安排路线、单日和途中调整；版本化方案、准确选择依据、报告预订、实际活动和结果通过现有 tasks/actions/共享 memory 留存。`travel.mjs` 只检查明确输入的时区、时间冲突、依赖和费用；真实路线、来源时效及库存仍需运行环境核查。只提供调研建议，不代订、付款、改签或取消；没有另建私人旅行数据库或自动监控服务。

购物共享规则在 `docs/domains/SHOPPING.md`：同款规格、报价条件、社区经验及质量依据、实际使用与售后、目标价关注分开保存。原件放在 `inbox/shopping/`，版本在 `records/shopping/entries/`；工具校验和算明确金额，专家判断适配与质量。关注队列读取已有数据，定时搜索与提醒由运行环境执行。

工作与职业记录的共享规则在 `docs/domains/CAREER.md`：项目设计、接受状态、实际工作、里程碑报告、成果反馈、职业机会和过程事件保存为带来源的不可改写版本。`career.mjs` 负责校验和描述性统计；职业教练判断卡点与下一步，主管家协调记录、学习与其他专家。通用助手任务完成与用户实际项目完成分别保存。

财务规则在 `docs/domains/FINANCE.md`：`finance-advisor` 给出自愿披露范围内的财务建议，主管家保存原件与版本化财务快照；`finance.mjs` 提供精确货币转换、单快照收支/余额/预算/目标/还款/情景计算。非数值披露描述先于快照正文读取，避免绕过拒绝。实际、计划、假设及来源/覆盖缺口分别保留；没有引入银行连接、私有数据库、交易或支付功能。

学习资源与 AI 教学的共享规则在 `docs/domains/STUDY.md`：统一学习 agent `study-coach` 按需使用规划、资源、教学和复盘模式，主管家保存课堂原答、材料引用和版本化续接检查点。当前使用已有 `tasks/`、`actions/` 与共享 memory；不另外建立模型专用学情库。交互式教学走 `/learn`，角色与工作流仍由共享目录发现。历史名称 `ai-tutor` 通过共享配置中的 `definitions.role_aliases` 指向 `study-coach`；旧定义归档到 `agents-disabled/`，旧资料与记录保留，模式切换不算新增专家或独立评估。

健康原件与结构化版本分别放在 `inbox/health/`、`records/health/entries/`，共享规则见 `docs/domains/HEALTH.md`。跨专家的持续问题、证据引用、提问与回答、关联假设和复查事项统一放在 `records/cases/`，规则见 `docs/core/COLLABORATION.md`；各专家读取同一份依据，由主管家转交和协调。记录更正会使旧依据需要重新评估，病例的协调状态与任务执行状态分别保存。

心理、情绪与人际互动规则在 `docs/domains/PSYCH.md`：`psych-coach` 按需支持倾听、反思练习、聊天措辞、送礼、合作分工和共同活动。主管家通过已有任务、行动和共享记忆保存原始对话、参与者同意、实际行动与结果，并保存版本化互动检查点。商品调研与正式项目规划仍由对应专家承担；没有新增心理评分、人脉数据库或自动联系他人的服务。

- **加专家**：一个文件即一位专家，需要时再配一个领域记录模板、知识库模板。所有流程通过 `node tools/experts.mjs` 动态发现，不写死名单。入口是 `/expert new`，由系统迭代师先调研、再起草。
- **加数据源**：一律先落到 `inbox/<来源>/` 并写来源说明，再映射进日志；需要定时的写成确定性转换脚本。
- **加日志字段**：改日志模板，并在 `docs/core/RULES.md` 登记。
- **加运行工具**：在共享配置文档登记接入方法，需要原生设置时放进 `config/runtimes/`；显式读取 `config/BOOTSTRAP.md`，不复制角色或新建厂商根目录指令树。

## 五、迭代线：系统自身的改进

调研报告、prompt 原文、借鉴来源属于**项目自身的迭代**，与健康等生活领域无关，全部集中在 `evolve/`，只由系统迭代师 `evolver` 维护：

| 位置 | 内容 | 是否随部署分发 |
|---|---|---|
| `evolve/README.md` | 本目录说明与部署边界 | 是 |
| `evolve/changelog.md` | 系统每次改动：改了什么、为什么、依据 | 是 |
| `evolve/lineage.md` | 每个 agent 借鉴了谁、待参考什么 | 是 |
| `evolve/candidates.md` | 候选 agent 清单及调研状态 | 是 |
| `evolve/research/` | 调研报告 | 否，只在开发目录 |
| `evolve/sources/` | 下载的 prompt / skill 原文（只读参考） | 否，只在开发目录 |
| `evolve/drafts/` | 新建 / 修改 agent 的草稿 | 否，只在开发目录 |
| `evolve/pending/` | 使用中提出的系统改动提案 | 否，只在个人库中产生，开发时审核 |

使用库只需要读懂迭代记录和 evolver 的写作位置；调研报告、下载原文和草稿体积大、只在开发过程中积累，还可能包含尚未采纳的提案和评审提示词，因此不复制进个人库。升级时，之前部署过且未被手动修改的调研/原文/草稿按下面的孤立文件规则移除；改动过的保留并报告。

迭代流程（新建或更新任何 agent 都走这条线）：

```
提出需求（新领域 / 反馈 / 无效建议 / 测试问题）
  → evolver 调研现成项目与论文方法（先查 evolve/，再联网）
  → 在 evolve/drafts/ 起草
  → 按用户已有授权落实；必要时确认未授权范围 → 管家落地到 agents/ 等位置
  → evolver 更新谱系、候选清单、迭代日志
```

使用中的学习回路（借鉴 Hermes Agent）：个人库里不直接改系统文件。用户纠正的默认做法和长期偏好写进有长度上限的工作笔记 `profile/working.md`，每次启动都显示；对流程的个人调整写进 `local/<同一路径>`，读完共享文件后再读它；值得推广的改动写成提案放进 `evolve/pending/`，由每周复盘汇总、在开发目录审核后发布。临时文件放在 `.lifeos/tmp/`，过期自动清理。细则见 `config/CONFIGURATION.md` 的 Working notes and local adjustments。

规则：**新建或大改任何 agent 前必须先调研**有没有别人做好的；领域专家文件只写领域内容，来源与借鉴只写在 `evolve/lineage.md`。

## 六、部署：开发与使用分离

| 目录 | 用途 |
|---|---|
| 开发目录（本仓库的 `lifeos/`） | 改系统、跑测试，使用虚构数据 |
| 个人库（你自己选择的任意目录，可以在同步盘里，也可以只在本机） | 只放你的真实数据 |

`node tools/deploy.mjs <目标> --apply`：
- 复制系统文件：规则文档、`agents/`、`workflows/`、`config/`、脚本、模板、参考数据，以及 `evolve/` 的说明、迭代日志、谱系和候选清单。
- 个人数据只在不存在时用空模板初始化，**永不覆盖**。
- 目标库里手动改过的系统文件（与上次部署记录的哈希不同）默认跳过，`--force` 才覆盖。
- 每次部署把复制的每个文件记进目标库的 `.lifeos-deploy.json` 清单；升级时用清单识别**孤立文件**（改过名、搬过位置或已从系统里删除，但目标库还留着的那份）：与清单哈希一致的未修改副本直接删除，删除后只剩空的目录一并清理，但不碰个人数据和用户自己维护的目录。改过的、或清单里没有的文件保留并报告，`--force` 才把原字节归档到 `agents-disabled/deployment-history/` 再删除。所有删除冲突在写入前先预检，和角色退役同一套流程。
- 没有清单的旧目标库不做任何删除，只做新增和初始化。
- 部署前检查共享入口和目录；目标库仍有旧厂商根目录文件时先报告并拒绝直接执行，经过内容核查与备份后再单独迁移，不自动删除旧内容。

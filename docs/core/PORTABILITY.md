# 文件与运行环境的迁移约定

LifeOS 的核心是同一套文件：个人数据、角色定义、操作流程、计算脚本和迭代记录。换模型或运行工具后，继续读取这套文件。

## 三种常见通用约定

| 约定 | 用途 | 适用范围 |
|---|---|---|
| `AGENTS.md` | 项目入口与工作约定 | 多种 agent 工具支持；不支持自动发现时，明确要求读取即可 |
| Agent Skills 的 `SKILL.md` | 可复用流程；YAML 元数据加 Markdown 正文 | 流程文件可以复用，自动发现目录和调用方式由运行工具决定 |
| MCP | 让运行工具访问外部工具与资源 | 统一工具连接协议；不是模型 API 配置格式，也不负责保存个人记忆 |

这三者均不保证所有模型 API 自动读取本地文件。原始 API 通常接收应用组装的请求；读取文件、提供工具和保存结果由运行工具或调用程序负责。

标准来源与本项目检查结果见 `evolve/research/2026-10-11-文件约定与项目检查.md`。

## 本项目的通用清单：`project.json`

这是 LifeOS 自己的项目清单，采用普通 JSON，供模型、运行工具或未来的适配程序读取；**不是各厂商共同识别的原生配置标准**。专家发现会读取角色目录，部署会读取入口和角色、流程目录，语言工具会读取默认语言及偏好文件位置；其他数据工具仍按现有文件约定执行。修改目录清单不会自动迁移已有文件。

- `schema_version`：LifeOS 清单格式版本。
- `prompt_language`：维护的结构化提示词语言，固定为 `en`；`language` 是默认交互语言，发布时为 `en`，首次初始化时由用户选择并保存到偏好文件。
- `timezone`：可选的默认时区；为 `null` 时使用运行环境的系统时区。解析顺序：用户偏好（`node tools/settings.mjs set timezone <IANA>`）、此项、`LIFEOS_TIMEZONE` 环境变量（测试或运行适配声明的主机时区）、系统时区。
- `interaction`：用户语言偏好文件的位置，以及首次初始化需要确认语言的约定。
- `review`：跨运行工具共用的最终审查轮数上限；审查流程与证据约定见 `docs/core/REVIEW.md`。
- `nutrition`：原图保存大小限制与通常的目标复盘周期；餐照、营养估算及记录完整性约定见 `docs/domains/NUTRITION.md`。
- `health`：健康资料原件大小限制，记录与来源约定见 `docs/domains/HEALTH.md`。
- `fitness`：训练导出与媒体原件大小限制，实际记录、计划、恢复和表现约定见 `docs/domains/FITNESS.md`。
- `collaboration`：跨专家问题的追问轮数限制；通用协作记录与版本约定见 `docs/core/COLLABORATION.md`。
- `research`：所有专家共用的轻量查询默认值与深入调研升级理由要求；执行约定见 `docs/core/RESEARCH.md`，运行环境仍负责实际调用。
- `entrypoints`：入口、说明、架构、规则文档的位置。
- `definitions`：角色与流程的目录，以及公共规则的位置。新增文件仍由扫描发现，不维护固定名单。
- `configuration`：专用适配文件的统一目录，以及禁止重新建立的厂商根目录入口。
- `data_directories`：个人数据和参考数据的位置。
- `evolution_directory`、`tools_directory`、`templates_directory`：迭代资料、脚本、模板的位置。

所有路径相对于本目录。清单不包含 API 地址、密钥、固定模型名称或运行工具的权限设置。

实际交互语言优先读取 `profile/preferences.json`，没有已保存的选择时使用清单默认值。运行 `node tools/language.mjs show` 可以直接得到有效语言和确认状态；首次交互按 setup 流程确认，确认后用 `set <language-tag>` 保存。个人偏好不属于部署时可覆盖的系统配置。

## 换工具时如何执行

1. 读取 `AGENTS.md`，按其中的意图路由只读取当前任务需要的文件；接入新工具、改配置或开发系统时，再读取 `config/CONFIGURATION.md`、`project.json` 和 `docs/core/HANDBOOK.md`，并按任务需要读取 `docs/core/ARCHITECTURE.md` 和 `docs/core/RULES.md`。
2. 日常记录、咨询、复盘等任务，读取对应的 `SKILL.md`，将用户输入作为 `$ARGUMENTS`。这里的 `/log`、`/review` 等是流程名称；新工具未必注册了同名快捷命令，直接用自然语言提出任务即可。
3. 需要专家时动态扫描角色文件，把其正文作为角色指令，并按要求读取公共规则和相关数据。支持子 agent 的运行工具可以进行独立调用；不支持时由主会话逐个执行角色流程，并如实标注执行方式。
4. 把 `Read`、`Grep`、`Glob`、`Bash`、`WebSearch`、`WebFetch` 等历史工具名称映射到当前工具的等价能力。它们不是所有 API 共有的工具名，也不自动形成权限隔离。
5. 在本目录运行 Node 脚本计算，按统一文件规则保存原始记录、建议原文和必要的更新。

6. 继续已有请求时读 `docs/core/CONTROL.md` 及任务当前状态。暂停、等待、取消、替换、计划版本和执行尝试都保存在普通 JSON 事件中，换模型后仍按这些状态判断。运行工具负责实际外部调用的停止；文件控制本身不具备所有工具共有的进程终止接口。

角色统一放在 `agents/`，流程统一放在 `workflows/`，操作规则统一放在 `docs/core/RULES.md`。根目录不再保留 `.claude/` 和 `CLAUDE.md`，也不为其他厂商建立平行的指令树。

共享配置入口是 `config/CONFIGURATION.md`，其启动提示词是 `config/BOOTSTRAP.md`；专用配置统一放在 `config/runtimes/`，保留工具需要的原生格式。Claude Code 使用显式参数加载适配文件和共享提示词，其他工具按自身能力读取相同入口，接入步骤均登记在共享配置文档。适配文件只保存运行工具的差异，不复制角色、规则或个人记忆。

运行 `node tools/check-layout.mjs` 可检查入口、目录、适配 JSON 及禁止的根目录文件；启动上下文和部署源验证也会执行检查。指令和原生权限不是操作系统锁，运行工具自身仍可能保存本地设置。已有旧入口的目标库在内容核查、备份和迁移完成前不能直接升级；脚本会报告问题，不自动删旧文件。

## 本库与其他工具共同管理同一份文件时

本目录默认由 LifeOS 自己读写，但也可以选择放在同步盘、网盘或备份工具管理的文件夹里。这些工具会让同一份文件出现在多台机器上，由此产生两类问题：写锁状态被复制，以及同一文件出现两份内容。两者都在普通文件层面处理，不依赖任何厂商。

**写锁是本机的，不写进本库。** 写锁只需要序列化同一台机器上的写入者，写进本库还会被同步或备份工具带到别的机器、或在释放后又被还原。锁目录因此放在系统临时目录附近，并按本库的真实路径区分，同一台机器上的两个副本不会共用一把锁：

- Windows 默认 `%LOCALAPPDATA%\lifeos-locks\<库路径哈希>`，其他系统默认 `$XDG_RUNTIME_DIR` 或系统临时目录。
- 环境变量 `LIFEOS_LOCK_DIR` 可指定位置（测试和特殊部署使用）。
- 锁不覆盖本库内容，删除锁目录只影响正在等待的写入者。

锁可能在写入过程中失效（进程被结束、机器断电）。`owner.json` 记录 pid、主机名和创建时间，只有确实失效的锁才会被清理：本机进程已不存在，或记录的主机名不同且锁龄超过上限（24 小时，远大于单次写入耗时）。另一台机器留下的锁在到期前不动，因为本机无法判断它是否仍在写入。同机的活锁永远不会被清除。`node tools/files.mjs locks` 只查看，`--clear-stale` 才清理可证明失效的锁；出现锁定错误时也会提示这条命令。旧版本把锁放在库内 `.lifeos/locks`，检查与启动只报告它，`locks` 命令会给出可安全删除的条目。

**冲突副本只报告，不自动处理。** 同步或备份工具在两端同时改动一个文件时，常保留第二份，例如 Seafile 的 ` (SFConflict 用户 时间戳)`、Syncthing 的 `.sync-conflict-时间戳-设备`、Dropbox 与 Nextcloud/ownCloud 的 conflicted copy、以及 `_conflict-时间戳`。`node tools/conflicts.mjs` 扫描本库，把每个副本映射回它对应的原文件，并按原文件分组输出；脚本只读取，不合并、不重命名、不删除。没有这类文件时它什么也不报，`LIFEOS_CONFLICT_SCAN=off` 可关闭检测，`LIFEOS_CONFLICT_PATTERNS=seafile,syncthing` 可只保留需要的形态。

副本会出现在启动上下文、布局检查和统计里：启动只打印条数与命令，不打印个人内容；布局检查把个人数据中的副本列为警告（不影响读取），把系统文件上的副本列为错误（工具与指令集会产生歧义）；`node tools/stats.mjs` 在文本与 `--json` 中列出存在副本的日期。处理方式由人决定：逐份对比副本与原文件，把采用的内容保存回原文件，确认后再删除副本。云端同步不是分布式锁，也不等于自动合并。

## 接入原始模型 API 时

日报也使用同一套 `docs/domains/REPORTING.md`、输入／睡眠事件模板和工具。晨间睡眠分析完成后，由执行模型调用共享事件接口导出前一天报告，不依赖固定时间或特定厂商任务系统。结构化原稿保留，PDF 为衍生输出；PDFKit 及字体属于库外的可选执行依赖，换机器生成 PDF 需准备相应运行库，读取已生成 PDF 不需要原机器字体。

调用程序负责读取这些文件、组织请求、执行获准的工具调用、保存返回结果。厂商的 endpoint、认证方式、模型名称、工具调用格式、流式输出和错误处理由运行环境或适配层配置。仅更换文件名或 `base_url` 不能保证各家接口完全兼容。

当前不建设 API 调用层。文件完整可读、规则明确、结果落盘，是这一阶段的迁移保证。

照片由运行工具提供实际图像读取能力，Node 脚本负责保存原件和计算。模型仅能读取文字时，可以接手已保存的图像描述、推断依据和营养 JSON；原图保留给后续支持视觉的模型重新分析。保存时不把文件名当成图片内容，也不声称文字模型能够读取尚未分析的图像。没有增加特定厂商的识图 API。

审查也使用普通文件：具体方案、每轮审查原文、来源哈希、问题分级和整改确认都保存在原请求的任务目录中。更换模型后按 `docs/core/REVIEW.md` 读取同一份审查包；脚本验证声明的审查步骤与存档绑定，不能保证新模型的审查判断与旧模型完全一致，也不自动判断每个未声明审查的请求是否应当审查。

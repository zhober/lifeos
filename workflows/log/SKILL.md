# Record a daily observation

Input: $ARGUMENTS

Use the quick path first. For a simple self-contained record stated in plain words, read `AGENTS.md` and `workflows/log/QUICK.md` and run `node tools/quick-log.mjs <input.json>`. That single command archives the verbatim statement, writes the canonical records through the existing domain utilities, projects them into the journal, runs the `day.mjs sum` equivalent, and returns a receipt. It needs no `work.mjs` request, plan, or step events, no critic, no expert role, and no memory entry unless the user stated a genuinely durable fact, preference, or constraint. Report the receipt and stop.

Leave the quick path for the full procedure below when the user asks for a plan, a comparison or a deep interpretation (short coaching suggestions stay on the quick path); when a document needs original-file import; when a record must be re-dated or retracted, or a non-meal record corrected (meal photos and meal corrections stay on the quick path); when the work needs several steps, waiting, external sources, or another role; when a concerning health or psychological sign is reported; when the record is a finance, shopping, travel, or career record; or when quick-log rejects the input.

Dating: interpret relative words such as "today", "midday", "this evening", or "last night" from the user's meaning. A message sent between 00:00 and 03:59 normally describes the day that just ended, so the journal date is that earlier day while the capture timestamp stays as reported. The quick path keeps the capture date on the raw-record line when it differs from the journal date. Sleep is stored on the waking date.

After actual morning sleep submission, follow docs/domains/REPORTING.md: retain sleep on its waking date, prepare a minimal sourced input, complete the relevant health analysis, save its exact input-bound artifact and invoke the after-sleep reporting hook for the preceding daytime date. For routine sleep the quick path satisfies this with a script-generated descriptive analysis (times, duration, user-supplied quality, no interpretation) and calls the same hook; a health-advisor or model analysis is only needed when the user reports concerning signs or asks for one. No fixed-time task, premature analysis/completion, diary backdating or compulsory private sleep input. Real automatic reports require an initialized vault; fictional development examples stay explicitly labeled.

Travel observations use docs/domains/TRAVEL.md. Preserve exact reports/originals and occurrence; link existing trip/task/design pointers without adding automatic travel journal metrics. A proposed or selected route is not a booking/visit, and a missed transport report requires an affected-plan proposal rather than silently changing a reservation. Retain source-bound actual activity/cancellation/outcomes through existing actions/memory and a new checkpoint when material.

Apply `docs/core/ORCHESTRATOR.md` to create or resume the personal request. For a compound record-and-advice request, complete recording and memory capture before consulting. Use `tools/files.mjs` for hash-checked organized writes and retain step artifacts under the request ID.

Declare capture steps as write effects under `docs/core/CONTROL.md`. Retain immutable request statements and write receipts as artifacts. A revised plan must not replay a successful recording operation; reuse validated results or create distinct authorized new work. Cancellation stops new processing while preserving records already written.

Follow the language policy in `AGENTS.md` (details in `docs/core/HANDBOOK.md`). Preserve the user's original statement verbatim. Use `templates/day.md` for exact persisted headings and table columns; the logical section names below do not rename that storage schema.

## Workflow

1. Determine the date. Default to today through `node tools/day.mjs path`; interpret relative dates from the user's meaning. A message sent between 00:00 and 03:59 usually describes the day that just ended. Assign sleep to the waking date.
2. Run `node tools/day.mjs new <date>` and read the journal.
3. Append the original statement to the raw-record section, with an HH:MM timestamp in the configured timezone (`node tools/context.mjs` or `node tools/settings.mjs show`) obtained through an available clock or equivalent date utility.
   For image-only input, append an attachment trace without fabricating user words. Preserve every original image through `tools/nutrition.mjs photo`; read docs/domains/NUTRITION.md and retain the returned path/hash in the request artifacts.
4. Organize the observation:
   - Meals: find a suitable exact entry with `node tools/food.mjs search <food>`, check quantities/preparation/intake, and calculate with `node tools/food.mjs calc "<matched-food> <grams>"` when useful. For a new source-traceable meal, save a `templates/meal.json` text observation through `nutrition.mjs record` and write its one canonical journal projection. A numeric table row alone remains legacy/unverified.
   - Meal photos: invoke the nutritionist's meal-estimation procedure through a vision-capable runtime, supplying original images, relevant text, known portion/recipe references, and restrictions. Group views of one meal, obtain the `templates/meal.json` structure, calculate it with `tools/nutrition.mjs calculate`, and save it with `record`. If vision is unavailable, save a pending image observation with unknown nutrition. The main assistant writes one journal projection with `meal:<meal-id>` and a canonical-record link; retain full estimates/ranges in that record. Do not log an extra meal for another view, a leftover photo, or an updated estimate.
   - Photo/meal corrections: use the existing meal ID and supersede its exact latest version; preserve old photos/assumptions, update only its organized projection, and reaggregate affected dates. Separate eating occasions remain distinct. A user statement confirming the whole day's intake may create a sourced coverage record; photo counts alone never confirm completeness.
   - Ingredient uncertainty: leave unknown contributions null by nutrient. Structural-zero claims require explicit applicable evidence under docs/domains/NUTRITION.md; a table/label zero alone is insufficient. Keep unknown amount/intake limitations visible even when some nutrients remain usable.
   - Independently reported day totals: preserve the source and use `nutrition.mjs independent` with explicit units/scope, instead of adding another meal or hand-filling a derived cache. Read conflicts and retained independent/recorded claims after aggregation.
   - If a portion is not specified, use an explicitly labeled quantity assumption/range when defensible, or retain it as unknown. Apply docs/domains/NUTRITION.md for photographic estimates, raw/cooked edible-weight basis, hidden ingredients, and actual consumption.
   - For prepared dishes absent from the database, check `data/food/custom.json`. Otherwise break the dish into ingredients, cooking oil, and accompanying staples; calculate each ingredient and combine the result. Record the assumptions and label the result as an ingredient-based estimate.
   - Do not accept a fuzzy match without checking that it represents the same food. Change the search or use a clearly labeled ingredient estimate.
   - Prefer nutrition labels for packaged foods. If the same prepared or packaged food recurs, suggest adding a reusable entry to `data/food/custom.json` using the format in `data/food/README.md`.
   - Exercise: apply docs/domains/FITNESS.md and fitness-session.json. Preserve one sourced canonical actual event with occurrence/subject, completion and recording completeness, explicit units/RPE scales, actual sets/load conventions/distance and optional exact plan link. Write one returned projection in the existing exercise table. Revise the same session for additional views/device evidence or corrections; reaggregate affected dates. Retain recovery/performance separately. Missing logs are not skipped workouts; clinical observations use docs/domains/HEALTH.md and shared references.
   - Study: use the existing study table and docs/domains/STUDY.md; preserve actual content/output, occurrence and reported duration. Do not infer duration, mastery or completion from an AI explanation, skipped lesson or suggested schedule. Link relevant lesson artifacts when available.
   - Work/career: apply docs/domains/CAREER.md. Preserve source words and occurrence, one canonical actual session or milestone/outcome/process statement through career.mjs record, and its link in the existing work section. Preserve explicit duration unit/basis/quality; unknown remains null. Revisions use the same record_id/exact supersedes. Plans, prepared/submitted/accepted outputs and actual application stages remain distinct. Do not add legacy work_h to session totals or treat an incomplete session sum as full-day work.
   - Weight, sleep times and duration, ratings, steps, water, and work hours: use the existing frontmatter keys. Distinguish measured values from interpretations of qualitative statements.
   - Thoughts/emotions and interpersonal events: use the existing mood-and-thoughts section and docs/domains/PSYCH.md. Preserve original words, actor/occurrence context and supplied score scales. Keep conversation/gift/cooperation suggestions separate from participant agreement and reported real actions/outcomes; simulations do not become personal events. Retain relevant source artifacts and sourced shared memories rather than a second contacts profile. Physical observations use the sleep-and-body section and docs/domains/HEALTH.md.
   - Shopping/ownership: use docs/domains/SHOPPING.md. Retain sourced product and actual order/use/return/refund/repair events through shopping.mjs; preserve subject/date/instance and distinguish proposed from observed. Link canonical versions in legacy purchase/wishlist summaries without overwriting old feedback or duplicating transactions. Supplied quotes, community excerpts and target-price decisions preserve price conditions/reading scope and exact product references; no automatic purchase or monitoring is implied.
   - Health symptoms/documents: apply docs/domains/HEALTH.md, retain originals/exact statements, and save typed versions with subject, occurrence precision, course, units/ranges, and review status. Link repeated observations to a shared case only when justified. An isolated episode can enter memory immediately. Do not infer a diagnosis or current medication use from historical data.
   - Domain records outside the daily template: discover experts with `node tools/experts.mjs` and append the explicit user record using the declared domain file's existing columns. Preserve the same original statement in the journal. If no role covers the event, retain it in the journal and mention the option of extending the roster.
   - Financial observations/plans: use docs/domains/FINANCE.md with permitted financial originals and one canonical scoped worksheet through finance.mjs. Preserve raw statements, source/subject/currency/period and actual/planned/cash-effect distinctions; link the record in the appropriate existing journal context without adding invented income/expense fields. A price quote, promise, credit-card repayment or recurring bill does not become a second consumption/actual payment. Store unresolved data in original artifacts and null fields rather than force a full financial intake.
5. Run `node tools/day.mjs sum <date>`.
   Capture new enduring facts, temporary constraints, relevant episodes, preferences, and attempted-method outcomes using `docs/core/MEMORY.md` and `tools/memory.mjs add`. A single episode is eligible immediately; do not apply the personal-pattern evidence threshold to events. Preserve original sources and distinguish occurrence time from capture time. Apply the same classification in every domain.
6. Reply with a concise recording confirmation, meal estimate/range where supported, and major assumptions. Distinguish numeric completeness, known subtotals, full-day scope, and source quality; unknown or disputed totals stay blank. Describe conflicts without discarding unrelated work/study data. Use eligible complete-day statistics for a requested target comparison. Do not call an unconfirmed/partial/unverified day reliable complete intake or diagnose low intake from missing records. Add a reminder only when an evident issue warrants it.
7. If material information is missing, ask a concise clarification while labeling any provisional estimate.

## Preservation

Do not remove existing information. A correction of an already recorded event updates its organized row while leaving raw statements intact; a separate occurrence is a separate event. Do not invent unreported observations.

# Shared configuration

This is the authoritative configuration policy for every LifeOS runtime. Read it with `project.json` and `docs/core/HANDBOOK.md` before adding or changing configuration, connecting a runtime, or doing system development; ordinary records and questions follow the routing in `AGENTS.md` without it. Its privacy section is the full voluntary-disclosure policy that workflows cite when they select personal context. Maintained machine instructions are English; user interaction follows `profile/preferences.json` and the language policy in `AGENTS.md` (details in `docs/core/HANDBOOK.md`).

Do not copy personal records, role prompts, workflow prompts, or operating rules into runtime adapters. A new model reads the same authoritative files. An adapter may describe capability mapping, native permissions, startup hooks, or prompt-loading flags; it must point back to the shared entry points.

Runtime-specific prose can use a named subsection below or a file under `config/runtimes/`. Create an adapter only when the runtime needs one, retaining its native file format. A larger adapter may have its own directory there. Register new startup procedures here rather than spreading them across project-root vendor files.

The shared `review.max_final_rounds` setting in `project.json` limits final critic rounds across runtimes, normally three. Review triggers and release rules live in `docs/core/REVIEW.md`; adapters do not override them or copy reviewer prompts.

The shared `nutrition` section sets the original-image size limit and usual target-review period. Meal/photo rules live in `docs/domains/NUTRITION.md`. Image understanding is a runtime capability: use an image viewer or caller-supplied image content; text-reading a path is insufficient. Preserve original bytes and textual/JSON observations so another model can continue. A runtime without vision stores pending observations instead of invented estimates; no provider API or global model route is configured here.

`nutrition.input_sanity_bounds` sets broad software checks for `age_years`, `height_cm`, and `weight_kg` before an eligible energy estimate. The defaults are [0, 125], [50, 260], and [10, 500] in those canonical units. They catch common unit/input mistakes; they do not define healthy ranges or clinical eligibility. Preserve explicitly supplied units and normalize only supported declared units under docs/domains/NUTRITION.md. The layout checker validates increasing finite nonnegative bounds. Keep any deliberate change here and in project.json, rather than in runtime-specific prompts.

The shared `health.original_max_bytes` limits retained health source-file size, normally 104857600 bytes. docs/domains/HEALTH.md defines source interpretation and typed records; the limit is operational, not clinical. `collaboration.max_question_rounds`, normally three, bounds one question thread under docs/core/COLLABORATION.md independently of final critic rounds. These model-neutral utilities retain documents and exchanges without OCR, clinical automation, model calls, background timers, or vendor message APIs. Runtime capabilities and docs/core/CONTROL.md govern actual execution. Keep these policies shared across adapters.

The shared `research` setting defaults to lightweight and requires a concrete reason before deep work. docs/core/RESEARCH.md is authoritative across domain experts, critic, evolver and future roles. It selects effort rather than lowering evidence/freshness requirements. Per-request explicit depth can override the default without changing global settings. The layout checker validates the entry point/default/reason flags; it does not measure research or invoke models. Keep one copy of the policy and reference it from roles/workflows.

`fitness.original_max_bytes`, normally 104857600, controls original export/media retention under docs/domains/FITNESS.md. Sessions, plans/adoption, recovery and performance are model-neutral personal records; exercise metrics are descriptive rather than clinical thresholds. Converters, vision, agent invocation and timers remain runtime capabilities. Layout validation checks this shared entry point/size setting, and deployment initializes empty data/reference templates without copying development training.

## Regional settings

No region is built in. project.json `language` ships as `en` and is only the default until the user chooses during setup; `timezone` ships as `null`, meaning the runtime system timezone. Tools resolve the timezone once through tools/lib.mjs (user preference, project.json, the `LIFEOS_TIMEZONE` declared host timezone, system clock) and validate IANA names; records keep the timezone actually used. Region (ISO 3166-1 alpha-2), currency (ISO 4217) and shopping channels are optional user preferences asked only when a domain needs them, under the voluntary-disclosure policy. `node tools/settings.mjs show` prints the effective values and sources; the layout checker validates their format. A runtime adapter may set `LIFEOS_TIMEZONE` when its host clock differs from the user's timezone; a saved user preference still wins. Do not change global machine settings for it.

## Project-root layout policy

docs/domains/REPORTING.md provides derived versioned daily JSON/Markdown/HTML/PDF after actual morning sleep submission and completed analysis, retaining the waking date. reporting.default_style is data_actions; trigger is after_sleep_analysis and sleep_date_basis is wake_date. The trigger is the submitted main sleep record for a waking date plus its completed analysis, at whatever clock time it is reported; there is no clock schedule. tools/report-sleep-analysis.mjs generates the routine descriptive analysis from the submitted bytes (interval, duration, user-supplied quality, limitations, analysis_method descriptive_script) so an ordinary daily report needs no model; the health-advisor procedure and also a model review apply only when the user reports concerning signs or asks for an assessment. A date holding nothing beyond the triggering sleep returns status skipped with reason no_permitted_content_beyond_sleep and writes no archive. A missing PDF renderer archives JSON/Markdown/HTML as generated_without_pdf and names the setup command instead of failing; --no-pdf remains an explicit text_only request. Archive and optional renderer paths are shared/layout-checked; reporting.domains is extensible. Lively presentation rules are shared in docs/domains/REPORTING.md, with one REPORT_LAYOUT_VERSION in tools/report-format.mjs for every export recipe; do not create per-provider theme prompts or personal scores. Core scripts remain dependency-free and PDFKit is a pinned optional external runtime under config/runtimes/pdf/ manifests. Installed packages, machine font/runtime paths and actual event support stay in the execution environment. Source classification/model sleep analysis remains caller work; no clock schedule, background watcher, API/model caller or online converter is enabled. Deployment seeds only empty report roots and never copies fictional exports/runtime packages.

reporting.cover_card_limit is normally four (allowed 1–4), and cover_domain_priority is an optional nonempty unique list of configured reporting domains. The default prioritizes nutrition, health/sleep and fitness before other available information. Unknown-only cards, empty domain sections and all-unknown trends are hidden in human views; original report.json remains complete. Known zero, sourced qualitative notes and material coverage/conflict warnings remain useful. Shared cover settings are bound into each PDF/text-only recipe, and are captured once for rendering; changing them creates a new export without rewriting old versions. Do not create runtime-specific copies or infer that working excludes learning.

docs/domains/TRAVEL.md uses existing tasks/actions/shared memory for versioned normalized itinerary designs, exact user selection, reported bookings and actual activities/cancellations/outcomes. travel.mode is research_and_advice_only and travel.login_handled_by is user. The layout checker validates these declarations and the shared entry point; generic deployment seeds only absent empty travel index/reference roots. tools/travel.mjs checks caller-selected normalized schedule/cost arithmetic without source-content reads, route/inventory/eligibility verification, FX, parsing or transactions. Current source/disclosure/selection interpretation remains coordinator/model work; there is no dedicated typed travel database, autonomous booking service, renderer or timer. Runtime-specific files do not override these boundaries.

docs/domains/FINANCE.md adopts immutable sourced cashflow/balances/budget/goal/debt/scenario worksheets and original exposure descriptors. finance.mode is analysis_and_advice_only; finance.original_max_bytes is normally 104857600. tools/finance.mjs performs local capture/metadata/read/arithmetic with saved field restrictions before stored contents are read. Source classification, additional disclosure tagging and actual advice quality remain runtime/model responsibilities. The helpers do not provide bank import/OCR, account access, securities prices, tax engines, Monte Carlo or automatic recurring payments. Generic deployment distributes the role/contract/tools/checkpoints and initializes only absent empty finance/reference roots.

docs/domains/PSYCH.md defines emotional support and interpersonal interaction through the single read-only psych-coach role. The shared psych entry point is layout-validated; generic deployment distributes the role/contract/checkpoint and initializes absent expert-reference files while preserving personal history. Original conversations, gift/cooperation proposals, participant agreement and actual outcomes use existing tasks/actions/shared memory. The pointer-oriented interaction checkpoint is a safe-write convention, not a dedicated clinical/interpersonal validator. Vision, independent model execution, external actions and timers remain runtime capabilities; no API routing, contacts database or automatic psychological score is configured here.

The shared shopping section declares original_max_bytes and optional discovery marketplaces/experience_channels lists, which ship empty: no marketplace is assumed. A user's channels are personal preferences (preferences.shopping, saved through tools/settings.mjs); a nonempty shared list applies only when the user has none. With neither, the shopping role asks when channel scope matters. The layout checker accepts empty lists and validates unique lowercase identifiers. These identifiers are lookup scope, not vendor API connections or claims of data access. docs/domains/SHOPPING.md is the sole quote/evidence/history contract; watch queues need runtime search/notification triggers. Deployment preserves legacy shopping tables/preferences and initializes absent empty source/reference roots.

shopping.mode is research_and_advice_only and shopping.login_handled_by is user. Layout validation rejects inconsistent values. docs/domains/SHOPPING.md defines the authoritative account/action boundary across main/expert/runtime calls. Users complete marketplace login themselves; authentication state stays outside the synced vault. Adapters may map available read-only browsing permissions, but must not override this boundary or embed credentials. The validator checks shared declarations, not actual browser clicks or OS permissions.

`career.original_max_bytes`, normally 104857600, limits retained source-file bytes under docs/domains/CAREER.md. Versioned work/project/opportunity/process records and descriptive quantities are model-neutral; parsing, model judgment, reminders and external applications remain runtime capabilities. Deployment creates empty record roots/reference templates and preserves personal history. No connection setting or employability/productivity score belongs here.

docs/domains/STUDY.md defines resource selection in the learner's language and AI teaching through existing task/action/memory files. study-coach is the single active learning role with planning/resource/teaching/review modes. The shared manifest registers the study entry point, and deployment seeds empty expert-reference templates. Video parsing, model calls and reminders remain runtime capabilities. docs/core/RESEARCH.md also defines the public-implementation check before introducing the next role; researched/drafted/implemented/verified states remain distinct.

definitions.role_aliases maps historical role identifiers directly to existing canonical active roles; aliases are not additional agents or independent reviewers. ai-tutor resolves to study-coach. Keep aliases in the shared manifest, not in runtime-specific routing copies. The layout checker rejects malformed/chained/self aliases, missing canonical definitions or a reactivated aliased role. Preserve the original retired prompt under agents-disabled/ and personal history under its original identifiers. New learning references use experts/study-coach/; existing experts/ai-tutor/ references remain readable, while fresh deployment skips seeding aliased expert folders.

During an explicitly requested upgrade, deploy.mjs previews retirement of an active alias. A role matching the prior deployment hash or the retained original prompt can be archived under agents-disabled/deployment-history/ and removed from active discovery. An edited/unmanaged retired role blocks apply before writes unless --force is selected; forced retirement still archives its exact bytes. Existing archive conflicts also block before writes. This narrow migration leaves personal records untouched and does not infer permission to deploy. A separate disabled role without a declared alias retains the existing roster-management procedure.

Do not create or restore `.claude/`, `CLAUDE.md`, `.codex/`, `.gemini/`, `GEMINI.md`, `.cursor/`, or equivalent vendor instruction/configuration trees at the vault root. The manifest lists entries checked by `node tools/check-layout.mjs`. `AGENTS.md` remains the shared entry point. Keep disabled roles in `agents-disabled/`, preserving their historical data.

When a tool offers to initialize a project or generate a vendor instruction file, use the shared bootstrap and explicit configuration loading instead. If it requires an incompatible root file with no alternate loading mechanism, report that limitation and keep LifeOS's shared files authoritative; do not silently generate a second instruction set.

Run the layout check after configuration or directory changes. The startup context utility and deployment source validation also run it. A failure identifies files or paths to review; the checker never deletes, moves, or repairs them. Preserve unexpected contents before any authorized reconciliation.

Instructions and native permission rules reduce accidental recreation. They are not an OS-level lock: runtime UI actions, permission persistence, bypass modes, and arbitrary subprocesses may still create files. Avoid project-local permission persistence or settings edits through a runtime UI; update the adapter file instead, then check the layout. A runtime that generates local state independently must keep that state outside the synced vault. Global runtime settings remain outside this project's scope.

## Voluntary disclosure and privacy

All personal information is voluntary, including health, body measurements, family, relationships, private conversations, work, identity/location and finances. This policy applies to the main assistant, every current/future expert, onboarding, memory retrieval, collaboration and critic review. Read the user-owned preference file from project.json interaction.preferences_file before personal questions or context selection; do not require a complete profile, questionnaire or uploads to provide permitted useful help.

Optional privacy.defaults sets a default mode and withheld_fields. Optional privacy.<scope> blocks use the same shape for subject scopes such as health, family, relationships, career, study, fitness, nutrition, identity, location or finance, including future scopes. Mode is null, general, ranges or detailed; withheld_fields is a unique list of lowercase identifiers. Existing privacy.finance remains valid unchanged. No migration, second preference list or selected mode is inferred from this generic feature request.

- general: do not solicit actual personal details; provide general explanations or clearly hypothetical examples.
- ranges: accept only approximate numeric ranges, anonymous labels or summarized qualitative information the user chooses to share.
- detailed: ask only relevant optional questions; no field becomes mandatory.
- null or absent: no chosen mode; keep questions proportionate, optional and skippable without requiring a privacy questionnaire.

An explicitly chosen subject mode replaces the default mode for that subject. For a request involving several applicable subjects, use the least disclosing applicable mode until the user gives a specific scoped instruction. Default and applicable subject withheld_fields are combined; a detailed mode never clears an explicit field restriction. Subject scopes identify the information, not the expert asking. Match synonyms and the user's actual meaning; an income restriction still applies when career-coach asks, and a health/relationship restriction cannot be bypassed by another role or label.

The reserved field identifier all can withhold every field in a default/applicable subject scope. A positive may_request_field result only means the saved mode/list does not block that normalized field; it never requires asking, authorizes broad record access, or overrides a current request-scoped refusal. Caller/model interpretation of synonyms, relevant scopes and the user's original restriction remains necessary.

Use node tools/privacy.mjs show <scope> [other-scopes] [--field <identifier>] for a read-only effective preference view, or read the same shared files directly. The helper projects saved modes/restriction identifiers; it is not permission to read every record or an automatic classifier of sensitive contents. Before loading personal originals, prepare the smallest permitted context; anonymous aliases and relevant excerpts are sufficient when full identities/history are unnecessary.

When a user explicitly declines information, accept it without asking why. Do not repeat, rephrase, delegate, use a substitute/proxy question or actively recover/infer the same withheld value from old files, attachment metadata, public clues or another person's records. Do not use/share a blocked value merely because it exists in a file. A request-only skip stays scoped; a persistent refusal is retained minimally until the user changes it. Silence is not a permanent refusal. Do not repeatedly ask the user to relax a restriction.

Save only actual user choices through the main assistant's hash-checked preference writes, retaining language/history/unrelated settings. Store scope/field identifiers and minimal policy history, not hidden values or an unsolicited reason. A user volunteering a value for a stated current purpose does not lift other restrictions or automatically reopen future questioning. This policy does not erase previously retained originals; input refusal, permission to use/share existing data and a deletion/retention request are distinct instructions.

Offer general methods, user-chosen ranges/anonymized descriptions or hypothetical practice without pressing for an alternative. Missing information stays unknown; never promote examples, assumptions, inferred motives or partial ranges into personal facts. If withheld inputs prevent a safe precise recommendation, qualify/limit that recommendation and continue useful independent work. Do not create indefinite waits for optional private fields or bypass existing safety/review requirements. Important safety support does not require coercing disclosure or assuming missing evidence proves reassurance.

Apply the same restrictions to context/review packets, expert handoffs and new summaries. Startup context reports date/language and journal existence only, without automatically printing personal metrics or reading journal contents before scoped permission. New vaults seed unselected defaults/empty restrictions; upgrades and language changes preserve existing choices, including legacy financial preferences.

These are shared prompt/context-selection rules and a read-only preference resolver, not encryption, an OS access lock, automatic data-loss prevention or an offline-data guarantee. The layout checker validates preference format; the selected runtime/caller must load and apply the policy. Do not claim live model enforcement from file tests.

## Shared startup procedure

1. Open the vault root as the working directory.
2. Load `config/BOOTSTRAP.md` explicitly when the runtime does not discover `AGENTS.md`. The bootstrap only points the model to `AGENTS.md`; a raw API caller must actually supply file contents or file-reading tools.
3. Read `AGENTS.md` and follow its intent routing. Read everything else on demand, never as a fixed preload: simple records and simple questions need only their quick guide; full workflows bring in `docs/core/RULES.md`, `docs/core/ORCHESTRATOR.md`, and the control, memory and domain documents they name; `docs/core/RESEARCH.md` only when research is actually needed; this document, `project.json` and `docs/core/HANDBOOK.md` for configuration, runtime connection, takeover or system development.
4. Run `node tools/context.mjs` for validated current context and the configured interaction language. A supported startup hook can run it; do not run it a second time just because a different model takes the role.
5. When a workflow needs a role, discover roles with `node tools/experts.mjs --all` and read the relevant files from `agents/` and `workflows/`. Native registration of slash commands or subagents is optional and runtime-dependent. Do not recreate vendor directories to obtain it. If independent execution is unavailable, follow the sequential role procedure in `docs/core/HANDBOOK.md` and disclose that mode.

This is a LifeOS file convention, not a configuration format recognized automatically by every provider. Runtime authentication, API endpoints, secrets, proxies, fixed model selection, and machine-specific routing belong to the execution environment; do not put them in this synced configuration or modify global connection settings during a project review.

## Claude Code

From the vault root, load the native adapter and the shared bootstrap explicitly:

```text
claude --setting-sources user --settings config/runtimes/claude-code.json --append-system-prompt-file config/BOOTSTRAP.md
```

The flags select user settings, load the specified adapter, and append the bootstrap. The bootstrap and the adapter's startup hook (`tools/context.mjs`) are both a few lines and only point to `AGENTS.md` routing, so an ordinary record or question does not load the larger contracts. Keep this loading method on subsequent launches. The adapter retains the existing startup context hook and data permissions, with native edit-deny rules for the old root Claude paths. Permissions use `Edit(path)` for file edits and writes. These rules do not constrain every subprocess or the runtime's own settings persistence. See the [CLI reference](https://code.claude.com/docs/en/cli-reference), [settings documentation](https://code.claude.com/docs/en/settings), and [permission rules](https://code.claude.com/docs/en/permissions).

Use the shared workflow names through natural language unless explicitly registered in the runtime. Roles and workflows in the neutral directories are not automatically native Claude Code agents or slash commands. Do not run initialization that generates `CLAUDE.md`, and do not use project-local settings persistence to store permanent approvals; edit `config/runtimes/claude-code.json` for authorized adapter changes.

## Other runtimes and raw APIs

For a runtime that reads `AGENTS.md`, follow its shared configuration reference. Otherwise supply `config/BOOTSTRAP.md` through the runtime's prompt-loading mechanism. Add a native adapter under `config/runtimes/` only when required, with its startup procedure documented here.

A raw API adapter is responsible for loading the authoritative files, mapping capabilities, executing authorized tools, and persisting outputs. Changing a provider does not require translating personal history or creating another memory store. This project currently supplies file contracts and Node utilities rather than an API invocation layer.

## Deployment and migration

The deployment script distributes shared instructions, neutral role/workflow directories, and `config/`, while preserving existing user-modified system files and personal data. Development backups and tests stay under the workspace's `test/` directory. Cloud deployment still requires an explicit user request.

Deployment records every file it copies in the target's `.lifeos-deploy.json` manifest. On upgrade it also reconciles that manifest against the current system set: a managed file the source no longer ships is an orphan. An orphan whose target bytes still match the recorded manifest hash is deleted, and any directory it leaves empty is pruned unless it is a personal or user-maintained directory. An orphan that was edited locally, or that the manifest never recorded, is left in place and reported; `--force` archives its exact bytes under `agents-disabled/deployment-history/` before removal. Removal conflicts are preflighted before any write, exactly like role retirement. A target without a manifest authorizes no removals, and personal data, seeded personal files and unlisted files are never removed. Evolution material follows the same rule: only `evolve/README.md`, `changelog.md`, `lineage.md` and `candidates.md` are distributed, since research reports, downloaded source prompts and drafts belong to the development copy.

Upgrading a vault that already contains vendor-root files requires a separate reviewed migration: the deployment script reports those root entries and refuses to apply an upgrade until their contents have been reconciled. It does not automatically remove old vendor directories, overwrite user edits, or treat a backup of user data as a runtime adapter.
